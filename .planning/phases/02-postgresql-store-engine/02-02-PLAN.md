<objective>
Deliver the atomic checkout with pessimistic row locking, and prove under live concurrency against Aiven PostgreSQL that RetailSync cannot oversell.

Purpose: This is the core value of the project, stock integrity under concurrent checkouts (STOCK-01..03). It completes DATA-01 by writing customers, orders and order_items. It also leaves the post-commit hook through which Phase 3 will publish `orders.placed`.
Output:
- `POST /api/carts/:cartId/checkout` and `GET /api/orders/:orderId`.
- The `OrderEventSink` hook point.
- `npm run test:race`, a live 3-scenario concurrency proof.
- Offline checkout and verdict tests.
- Checkout steps in the live API smoke run.

Scope guard: backend only (the user excluded all UI work; do not touch `frontend/`). Do NOT implement Kafka publishing or OpenSearch sync; that is Phase 3, and this plan only defines and invokes the no-op hook. No schema migration is needed: `orders.cart_id UNIQUE`, `inventory_stock_quantity_nonnegative` and the inventory unique key already exist in `backend/src/db/schema.sql`. No new npm packages.

Isolation choice (STOCK-01 "serializable/pessimistic"): use pessimistic locking under PostgreSQL's default READ COMMITTED with explicit `FOR UPDATE` row locks, not SERIALIZABLE. Row locks fully serialize contended inventory rows without 40001 retry storms under the flash-sale load.
</objective>

   - Inside ONE `db.transaction`, in this exact order:
     - (a) Lock the cart: `SELECT c.id, c.status, c.location_id, l.name AS location_name, l.city FROM carts c LEFT JOIN store_locations l ON l.id = c.location_id WHERE c.id = $1 FOR UPDATE OF c`.      - (c) Upsert the customer: `INSERT INTO customers (name, email) VALUES ($1, $2) ON CONFLICT ((lower(email))) DO UPDATE SET name = EXCLUDED.name RETURNING id`. Do this before the inventory lock so the critical section stays short.
     - (d) Lock the inventory rows with the schema.sql contract query, kept verbatim on ONE line: `SELECT id, product_id, stock_quantity FROM inventory WHERE location_id = $1 AND product_id = ANY($2::bigint[]) ORDER BY id FOR UPDATE`. Pass the product ids sorted ascending.
     - (e) Check stock in TypeScript. A product with no locked row (the store does not carry it) has available 0. Collect every shortfall and throw AppError 409 `OUT_OF_STOCK`. Throwing inside the transaction makes withTransaction ROLLBACK.
       - Message: `Insufficient stock at {locationName}: {name} (requested N, available M)`, with multiple shortfalls joined by `; `.
       - `details`: `{ locationId, locationName, items: [{ productId, sku, name, requested, available }] }`.
     - (f) Decrement in one set-based statement: `UPDATE inventory AS i SET stock_quantity = i.stock_quantity - d.qty FROM unnest($1::bigint[], $2::int[]) AS d(id, qty) WHERE i.id = d.id RETURNING i.id, i.product_id, i.location_id, i.stock_quantity`.
     - (g) Insert the order: `INSERT INTO orders (customer_id, cart_id, location_id, total_amount)`. Compute `total_amount` in SQL as `sum(q * p)` over `unnest($n::int[], $m::numeric[])`, passing the price strings read in (b). Return `id, status, payment_status, total_amount, created_at`.
     - (h) Insert the order items: `INSERT INTO order_items (order_id, product_id, quantity, unit_price)` from unnest arrays, returning `line_total`. Unit prices are the product prices read in (b); the client never supplies prices.
     - (i) Mark the cart: `UPDATE carts SET status = 'checked_out', customer_id = $2 WHERE id = $1`.
     - Build the order view and the OrderPlacedEvent from the returned rows.
