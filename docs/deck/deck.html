RetailSyncProblem and existing gap

The last unit sells twice.

The problem
A chain that sold only in stores goes online across India. Many shoppers press buy on the same item at the same moment.
Who is affected
Shoppers whose paid orders get cancelled, staff fixing stock by hand, and the business paying refunds in every sale.
Current solutions
Carts that read stock and write it later, nightly syncs between store and site, keyword-only search.

Overselling

Check then write, under load, sells one unit to two people.

Stale stock

Search and listings lag the database, so gone items still show.

Rigid search

"bluetoth" finds nothing, and there is no filter for what your own city has.

RetailSyncProposed solution

One truth. Events for the rest.

PostgreSQL decides every sale under a row lock. Kafka tells the rest of the system what happened. OpenSearch answers searches with live stock.

How it solves it

Checkout locks the exact stock rows, so two buyers can never take the same last unit.

Always current

Each committed order becomes a Kafka event; consumers update the search index in seconds, not overnight.

Why it is better

The database guarantees correctness, and a live ledger shows every step as it happens.

RetailSyncArchitecture and tech stack

Input, process, output.

Input
Storefront

React shopper browses, searches, adds to cart, checks out.

Process 1
Fastify API

Validates input, runs the locked checkout transaction.

Process 2
PostgreSQL

Rows locked in a fixed order, stock decremented, order written, committed.

Process 3
Kafka

orders.placed, then a consumer publishes inventory.updated.

Output
OpenSearch

Search-sync consumer reindexes the product; search shows the new stock.

Frontend React 18, Vite, Tailwind. Backend Node.js, Fastify 5, TypeScript, zod. Data Aiven PostgreSQL 18, Aiven Kafka 4.3 (KafkaJS), Aiven OpenSearch 3.6. Hosting Render, credentials only in environment variables, TLS verified to the Aiven CA.
